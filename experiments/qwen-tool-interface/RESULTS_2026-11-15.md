## Pass 0 — Forensic result that prompted the experiment

The earlier **open-ended game coding** attempt, https://github.com/AlterProgramming/Kairos/actions/runs/43759415819, exhausted seven turns on a repeated read/edit cycle. It repeatedly used `search term from the source` and `exact source text` as literal arguments, generated large, incomplete edit JSON, never applied a source change, and never reached Kairos/Studio. This does **not** establish that the base model is intrinsically unable to search code: the homemade prompt included these literal pseudo-argument examples, the conversation expanded, and the source and task instructions were mixed.

## Pass 2 — Native function schema and source literal constraint

`probe_window.py` retained the actual official tool schema while **explicitly** requiring `query` to be literal characters found in source, never the description of the user's objective. Source excerpt sizes varied independently at 220, 1500, 4000 **characters** (not token lengths). Sampling temperature 0.7, top-p 0.8, top-k 20.

| Case | Source window | Result |
|---|---:|---|
| B1 native sampled | 220 chars | Exact `function begin()` |
| B2 native sampled | 1500 chars | Exact `function begin()` |
| B3 native sampled | 4000 chars | Exact `function begin()` |
| B4 native different seed | 220 chars | Exact `function begin()` |
| B5 native, good example for *other* function | 220 chars | Exact `function begin()` |
| B6 JSON different seed | 220 chars | Source-grounded `function begin` |
| B7 plain text | 1500 chars | Source-grounded `begin` |

**7/7 valid substrings; native 5/5 exact.** In those native cases the complete tool calls were syntactically valid `<tool_call>...` invocations with `read_source` and a literal code query, not a framework-injected action. Timing of B1/B2/B3 generation (single seed and host): ~5.4 s / 8.4 s / 15.6 s, respectively. This suggests increased context can cost computation; it does NOT establish an optimal context window. B1/B2/B3 all succeeded.

These calls were *model generated*, but source was placed directly in the prompt; this result establishes local grounding, **not** autonomous search, browsing, tool execution, or code editing.

## Pass 3 — Four-function semantic distractor control

`probe_distractors.py` showed all four actual function declarations and ~360 source characters for each: `begin()`, `pulse()`, `finish(win)`, `spawnEnemy(i,boss)`. It then requested one function by its *behavior*, not its name. All used the same native schema, same visible source collection, sampled decoding with different fixed seeds:

| Request | Actual Qwen query | Outcome |
|---|---|---|
| Initialize new battle and wave | Began very long literal implementation; truncated JSON at 110 tokens | **No valid call** |
| Spend energy on area ability | `function finish(win)` | **Wrong function**, but source-grounded |
| Reward and advance after battle | `function finish(win)` | **Correct** |
| Construct and add enemy | `function spawnEnemy(i,boss)` | **Correct** |

**2/4 exact semantic targets**, **3/4 parseable source-grounded queries**. Critically, B's 5/5 exact result does not generalize to C's multi-candidate discrimination. The observed distinction is between lexical extraction and choosing the right symbol based on meaning.

## Pass 4 — Operational representation

This is a **failure decomposition**, not a blanket intelligence ranking:

- **Evidence of useful capability:** Can generate a correctly formatted native function call with an exact, visibly grounded literal source query, including when a different example is shown; observed on several short-to-medium windows and seeds.
- **Unreliable in measured conditions:** Choosing the semantically correct function among multiple plausible code contexts; avoiding overlong, truncated tool arguments; correcting an unsuccessful schema response after feedback in the A1 condition; independently making validated edits (not tested in these read-only experiments).
- **Important distinction:** Tool syntax, argument literal grounding, semantic target selection, tool execution, and achievement of an original product goal are five separate gates. Never merge them into one `PASS`.
- **Potential composition, not yet demonstrated:** Let a small model propose candidate source identifiers in compact, relevant contexts; verify that they occur in source; use independent judgment or another model to decide which identifier actually answers the user's intent; use Kairos for bounded, separately authorized execution; retain failures and escalate rather than repeating identical invalid actions. This is a proposed allocation of responsibilities, **not** a proven improvement to complete developer output.
- **Interface recommendation grounded by these trials:** Avoid pseudo-tool examples with placeholders as literal values. Present the actual Qwen tool schema and explicitly distinguish source substrings from natural-language task descriptions. Parse the tool call without automatically replacing its generated arguments; that would invalidate tests of model competence. Source-hit validation is a *separate* deterministic tool step.
- **Next independent check (not executed):** Test the same tool-interface variants on a genuinely unrelated repository and larger semantic distractor set, with frozen prompts, multiple seeds, and compute/tokens measured. Do not claim broad transfer based on Forge Arena.

### Controls, accounting, limitations

No model fine-tuning was performed; no claims about the saved LoRA's general coding capability are made. The tests used an actual game source, **not** a synthetically favorable fake source, but source snippets containing the relevant declarations were deliberately provided and this can simplify the task. Tiny N and one repository disallow statistical claims about broad model reliability. Greedy and sampled decoding differed in some runs; do not conflate them. Earlier failed experimental CI runs before model inference were attributable to runner path/checkout setup, not model behavior.
